% ABSTRACT
% ==========================================
\begin{abstract}
Edge-based academic installations are typically unmonitored embedded appliances that are placed in an environment where infrastructure resources are limited. The ability to operate in these conditions is mainly related to the degree of reliability of the operating system and updates rather than the accuracy of the applications. Mostly because the devices need to function reliably under varying loads, which is a limiting factor in their adoption for institutional academic settings. Therefore, in such cases, the OS configuration and updates are becoming more critical to ensuring the overall performance and functionality rather than the underlying application.

This study presents an invariable edge deployment architecture targeting the enhanced resilience to corruption and self-healing capabilities in the presence of power and network supply fluctuations. We propose an Appliance Invariance Model that utilizes a read-only OverlayFS rootfs, thus isolating all writes in the system to either volatile memory or persistent storage in the form of versioned containers. An extended safety is achieved through watchdog-based hardware monitoring of inference queue liveliness, as well as a Blue/Green OTA update procedure with an automated rollback mechanism.

A controlled testbed subject to frequent hard power cycles and update failures shows reliable reboots and automated recovery. The resulting system shows the potential improvements in the reliability of distributed academic embedded appliances to be gained by disciplined operating-system immutability and automated lifecycle control.
\end{abstract}

\begin{IEEEkeywords}
Immutable Appliance Architecture, Lifecycle Hardening, OverlayFS Invariance, Bounded Recovery, OTA Rollback, Zero-Touch Provisioning.
\end{IEEEkeywords}

% I. INTRODUCTION

\section{Introduction}

The author submits that the primary thesis is that the development of non-modifiable appliances significantly contributes to optimal functioning under unstable supply voltages. Upon the initial deployment in abandoned environments, such devices’ functioning is predominantly determined by the underlying operating system’s update security and reliability rather than the inherent application stability \cite{b1, b2, b3}.

\subsection{Operational Fragility of Mutable Edge Hosts}
A conventional Linux system with a writtable root filesystem will develop configuration drift due to mutable updates at the level of individual packages. This is caused by arbitrary writes and subsequent state mutations. The result of such instability is that the system becomes more susceptible to filesystem inconsistencies on every reboot following a sudden power loss and every update which introduces new dependencies \cite{b4, b12, b17}. Unattended devices cannot rely on manual remediation---intermittent infrastructure conditions (unstable power, wireless congestion, restricted physical access) destabilize traditional deployment assumptions. Lifecycle instability emerges structurally from mutability, not merely from poor maintenance practices.

\subsection{Contributions and Subsystem Scope}
This paper details an immutable, containerized OS architecture designed for Zero-Touch administration. By enforcing strict separation between a read-only host OS and containerized inference logic, we ensure that the edge node can survive power loss, recover from software hangs, and securely update its models without human intervention. Specifically:
\begin{itemize}
    \item We formalize an Appliance Invariance Model that confines all runtime mutations to volatile memory or versioned container layers.
    \item We implement Blue/Green OTA rollback as a bounded-failure containment mechanism.
    \item We integrate hardware watchdog recovery for liveness enforcement under scheduler exhaustion.
    \item We validate autonomous recovery across 50 simulated hard power-cycles.
\end{itemize}

Within the ScholarMaster architecture, this subsystem enforces immutable lifecycle behavior, hardens OTA recovery, and stabilizes unattended appliance deployment only. It does not optimize flash endurance (Paper 12), validate runtime enforcement semantics (Paper 18), optimize federated adaptation (Paper 13), derive formal verification theorems (Paper 21), or define architectural privacy doctrine (Paper 17).

% II. FAILURE-STATE TAXONOMY & RELATED WORK
% ==========================================
\section{Failure-State Taxonomy and Related Work}

To analyze deployment reliability systematically, we categorize the primary failure classes encountered in unattended edge appliances:
\begin{itemize}
    \item \textbf{Power-Loss Corruption:} Unclean shutdowns mid-write causing OS unbootability (addressed via Appliance Invariance and OverlayFS).
    \item \textbf{Kernel Deadlock / Scheduler Exhaustion:} Total system freezes where software supervisors fail (addressed via Hardware Watchdog integration).
    \item \textbf{Application Crash:} Container-level segfaults or memory leaks (addressed via daemon process supervision and cgroup isolation).
    \item \textbf{Malicious Update Injection:} Poisoned firmware or rogue container deployment (addressed via TPM Secure Boot and pre-flight OTA validation).
    \item \textbf{Network Partition:} Multi-day loss of cloud connectivity (addressed via priority-aware buffering).
\end{itemize}

\subsection{MLOps for Edge Devices}
Although MLOps is well-established for cloud infrastructure, the same practices have been less explored for distributed edge deployments. Specifically, we note that Sculley et al. \cite{b5} identified ``hidden technical debt'' in ML systems which proves particularly challenging in the context of distributed and constrained hardware lacking the reliability of data-center grade power supplies. Edge deployment pipelines are typically not battle-tested in the same way as their cloud counterparts and have to tolerate ``dirty'' power. We adopt concepts from cloud-native container orchestration \cite{b8, b9, b10} and apply them within the embedded Linux environment using kernel isolation and daemons supervision as a foundation.

\subsection{Embedded Reliability and Filesystems}
Flash-based storage systems pose new reliability challenges for devices which are subject to power instability (as is the case for many embedded systems) \cite{b12}. Journaling filesystems (e.g., Ext4) protect against some sources of metadata corruption, but are not immune to failures in the underlying flash translation layer during an active block write \cite{b14}. The use of structural immutability for the purpose of defining read-only root structures is promising in terms of extending the lifespan of flash storage \cite{b13}, but carries implications for volatile memory management in high-throughput, log-intensive edge appliances, which could cause memory-swap thrashing and OOM (out-of-memory) cascades if not properly handled.

% ==========================================
% III. APPLIANCE INVARIANCE MODEL
% ==========================================
\section{Appliance Invariance Model}

The proposed deployment model treats the edge node as an immutable appliance instead of a conventional mutable Linux host. The system architecture and end-to-end data pipeline are defined by the broader architectural series; this work focuses on the lifecycle invariance properties of the deployment substrate. The deployment model intentionally avoids traditional package-manager operations such as remote apt-based upgrades executed through SSH. Instead, the host OS is treated primarily as a minimal read-only container runtime environment. All software dependencies, drivers, analytic logic, and neural network models are packaged into immutable Docker images \cite{b8}.

\subsection{Formal Invariant}
The architectural principle underlying this deployment strategy is formalized as the Appliance Invariance Model. Let $H$ represent the lower-layer persistent filesystem state, $C$ represent the containerized application state, and $V$ represent the volatile overlay state. The core system invariant is:
\begin{equation}
\forall t,\; H_{persistent}(t) = H_0
\end{equation}

This invariant expresses the design principle that the persistent host OS state remains unchanged during routine operation. Invariance is enforced through \textbf{mutation confinement}: runtime mutations are restricted either to volatile memory ($V$)---which is destroyed on power loss---or to versioned container layers ($C$) managed through controlled OTA transitions. The difference is crucial: The persistent immutable state ($H_0$) - this is such state which is never, ever written during normal operations. The volatile operational state ($V$), into which all the writes go, serves as the working area, the place where all the computation happens. The state of the containerized application ($C$) can be changed only through authorized OTA upgrades which implies that the state transitions are controlled and verifiable. Finally, the runtime state changes only inside memory (RAM). This way, any corruption is confined within its space and the power cycle resets it to a clean state. This prevents accumulation of filesystem changes on every reboot.

% IV. RELIABILITY ENGINEERING

\section{Reliability Engineering}

System reliability emerges from the interaction of several complementary mechanisms implemented at the operating-system level. 

\subsection{Process Supervision}
The inference engine is operationalized as a system daemon using strict process-orchestration policies \cite{b16}. The unit configuration (Listing 1) defines strict restart policies. The \texttt{OOMScoreAdjust} directive explicitly protects the primary Docker daemon and SSH server from the Linux Out-Of-Memory (OOM) killer, shifting most memory exhaustion risk to the individual user-space containers which can be safely restarted without bringing down the host OS or losing network connectivity.

\begin{figure}[htbp]
\textbf{Listing 1: Supervisor Production Unit}
\begin{lstlisting}[language=bash]
[Unit]
Description=Edge Analytics Appliance
After=network.target docker.service
StartLimitIntervalSec=0

[Service]
Type=simple
Restart=always
RestartSec=3
User=root
# OOM Score: Protect Host Docker Daemon
OOMScoreAdjust=-1000
ExecStart=/usr/bin/docker-compose -f /opt/deploy.yml up
# Watchdog Integration
WatchdogSec=15s

[Install]
WantedBy=multi-user.target
\end{lstlisting}
\label{fig:systemd}
\end{figure}

\subsection{Hardware Watchdog Timer (WDT) Integration}

Software-level process supervision alone cannot recover from all classes of runtime failure. To address this, we enable the hardware Watchdog Timers (WDT) integrated into commodity ARM-based edge compute modules to provide hardware-level liveness enforcement for appliance survivability \cite{b15}. The watchdog ensures recovery under liveness failure; detailed runtime enforcement semantics and invariant verification are addressed in the architectural verification layer of the broader series.

\subsection{Read-Only Filesystem (OverlayFS) Mechanics}

Filesystem immutability is implemented using the OverlayFS union filesystem provided by the Linux kernel. To substantially reduce the likelihood of storage corruption during rolling blackouts, the root filesystem is mounted as read-only using OverlayFS. 

The physical storage acts as the immutable Lower Directory. A volatile \texttt{tmpfs} (RAM disk) is mounted as the Upper Directory. The operating system interacts with the Merged View. All system writes (logs, temp files, state changes) are seamlessly intercepted by the Linux kernel and written exclusively to the volatile RAM disk. 

Under this configuration, abrupt power removal destroys only the volatile UpperDir residing in RAM. Because persistent storage is mounted read-only during normal operation, boot-sector and base OS corruption events were not observed during evaluated power-cycle tests. OverlayFS isolation confines volatile churn to bounded RAM---corruption domains become spatially limited, and reboot semantics inherently restore clean operational state. This architecture improves bounded recoverability rather than guaranteeing absolute corruption impossibility; hardware-level flash failures, bootloader corruption, and power-delivery anomalies remain outside the OverlayFS protection boundary.

\subsection{RAM-Disk Exhaustion Mitigation}
To reduce the risk of RAM exhaustion, log output is aggressively bounded. System and container logs are capped, and cgroup-based memory ceilings are applied to inference containers. Because operational telemetry is streamed off-device when connectivity permits, deep local log retention is intentionally avoided.

% ==========================================
% V. OTA UPDATES & FLEET MANAGEMENT
% ==========================================
\section{OTA Updates \& Fleet Management}

Maintaining a distributed fleet of edge appliances requires deterministic and failure-tolerant update mechanisms. Deploying updated neural network weights, system dependencies, or application logic across a fleet requires fail-safe OTA mechanisms \cite{b18}. We implement a Blue/Green deployment state machine leveraging container APIs to provide deterministic cutovers with minimal service disruption \cite{b9}. The Blue/Green mechanism functions as a \textbf{bounded-failure containment mechanism}: OTA rollback constrains update blast radius, pre-flight validation limits irreversible deployment transitions, and deterministic reversion improves unattended survivability.

\subsection{Deterministic Cutover Formalization}
We define the update timing constraints as follows. Let $T_{pre}$ be the validation time, $T_{cutover}$ be the container swap execution, and $T_{rollback}$ be the revert time. 

In practice, the cutover process is designed to avoid user-visible downtime. The currently active container (Blue) continues serving until the incoming container (Green) passes health checks. Once it does, hardware access is redirected back to the new instance. As can be seen, there were only a few seconds of downtime as the switch from one instance occurred, but no interruptions to the service were reported during the test runs.

The state machine operates as follows:
\begin{enumerate}
\item \textbf{Pull (Delta):} The device downloads the new container image (Green) alongside the running container (Blue). To conserve constrained academic network bandwidth, we utilize registry delta-compression, pulling only modified layers.
\item \textbf{Pre-Flight Test:} Green is started without hardware camera bindings. It executes an internal self-test (verifying weight checksums, loading libraries, and allocating runtime contexts).
\item \textbf{Cutover:} If the self-test passes, the supervisor tears down Blue, binds the hardware to Green, and elevates it to primary.
\item \textbf{Automated Rollback:} If Green crashes or fails to emit a successful inference heartbeat within 60 seconds, it is destroyed, and Blue is instantly restarted.
\end{enumerate}

% ==========================================
% VI. OPERATIONAL CONFIGURATION POLICIES
% ==========================================
\section{Operational Configuration Policies}

The appliance configuration translates systemic design constraints into OS-level strictures. We enforce compliance via an automated deployment checklist applied to the base image:

\begin{itemize}
    \item \textbf{Volatile Mount Enforcement:} \texttt{/var/log}, container volumes, and local telemetry buffers are all mounted to \texttt{tmpfs}, which ensures that they can't be persisted to physical media. This is enforced by checking their mounts during the boot process.
    \item \textbf{Swap Disablement:} \texttt{swapoff -a} is enforced. This guarantees that application memory buffers are never inadvertently paged to physical disk by the OS memory manager under load.
    \item \textbf{Encrypted Keystore:} Any persistent identity configuration keys or certificates required for network provisioning are stored on encrypted partitions and managed strictly through secured key services.
\end{itemize}

\section{Network \& Data Resilience}

Edge appliances are often expected to operate in campus networks where they can be subject to long network partitions. During such periods of downtime, telemetry data is gathered in volatile memory on the edge appliance and later sent once connectivity is re-established. The buffering mechanism stores the telemetry data in an SQLite instance that is resident in memory.

% VIII. DEFENSE-IN-DEPTH SECURITY
% ==========================================
\section{Defense-in-Depth Security Architecture}

Devices operating on open campus networks require robust physical and transport-layer security configurations to mitigate the risk of unauthorized firmware modification or network impersonation \cite{b16}.

\subsection{Zero-Touch Provisioning (ZTP) Sequence}

In order to achieve the Zero-Touch administration, devices are onboarded automatically. Additionally, cryptographic lifecycle management is automated as well using Trusted Platform Module (TPM 2.0) \cite{b19} hardware security module available in edge board.

On first boot, the device contacts the provisioning server. The device uses the factory fused TPM endorsement key (EK) to assert its hardware identity to the provisioning server over PKCS\#11 interface. On successful authentication, the server issues a unique short lived X.509 certificate to the device. The private key of this certificate is generated inside the TPM and not accessible. The device retrieves its operational configuration.

\subsection{Mutual TLS (mTLS) \& Secure Boot}
After Zero-touch provisioning (ZTP), all communication with the central fleet manager is secured by Mutual TLS (mTLS) using TLS 1.2 or higher \cite{b23}. During this step, the edge node is authenticated, and the server is authenticated with the edge node using a TPM-backed certificate.

The TPM-backed certificate lifecycle reduces the risks of extraction of a private key by relying on a secure hardware module to store it. Similarly, Secure Boot decreases the probability that an arbitrary kernel or bootloader will be run on the device. These measures are all about lifecycle integrity: trusting that the deployment to be operated on is authentic reduces the risks of exfiltration, tampering, or unauthorized updates. In more detail, the threat modeling process is covered in later sections of this series, so we have left out some specifics that would make this post even longer than it already is.

% ==========================================
% IX. FULL-STACK OBSERVABILITY
% ==========================================
\section{Full-Stack Observability Pipeline}

Operational reliability across a distributed fleet requires continuous system observability. The fleet-management layer implements a pull-based monitoring architecture built around Prometheus \cite{b22}, optimized for intermittent edge connectivity.

\subsection{Metrics Schema and Local Buffering}
A custom Python \texttt{prometheus-client} exporter runs on each node, exposing hardware and application metrics. Metrics are categorized into liveness, thermal, and network-stability domains, enabling fleet-wide anomaly detection via threshold-based alerting.

During network partitions, the central Prometheus server cannot scrape the edge nodes. To prevent metric loss, the edge nodes utilize a local Prometheus Pushgateway or remote-write buffer. High-cardinality metrics are downsampled locally during outages to conserve memory, ensuring that essential fleet health data is preserved and successfully transmitted once connectivity is restored.

\section{Fleet Lifecycle Validation}

The reliability mechanisms described above were evaluated through a controlled lifecycle validation testbed. Validation was conducted on a controlled testbed designed to simulate fleet conditions. We evaluated the critical lifecycle mechanisms (OTA, Watchdog, Provisioning) independently of inference performance. Results reflect this specific hardware configuration and may vary depending on flash controller firmware.

\subsection{Power Failure Recovery Validation}
To evaluate corruption resistance under the Power-Loss Failure class, we subjected the OS architecture to 50 simulated hard power-cycles, utilizing power cuts randomized between 0.5--3.0s intervals during peak I/O stress tests via automated relay switching.

\midrule

Within the evaluated deployment conditions, across 50 induced abrupt power interruptions under active I/O stress, no boot-blocking corruption events were observed in the OverlayFS configuration. In contrast, the standard writable Ext4 configuration required manual intervention in 6 cases. While the sample size is limited and recovery timing depends on board and bootloader characteristics, these results are consistent with improved recoverability through mutation confinement. Long-duration fleet behavior under multi-year continuous operation remains deployment-dependent.

\subsection{OTA Rollback Validation}
To test the resilience against the Malicious/Corrupt Update Failure class, we intentionally pushed a poisoned container image (configured to segfault upon initialization) to the edge node.
\begin{itemize}
    \item \textbf{Detection Time:} 4.2 seconds (Pre-flight test failure).
    \item \textbf{Rollback Execution:} 2.8 seconds (Green destroyed, Blue resumed).
    \item \textbf{Total App Downtime:} No user-visible interruption was observed; internal container handoff latency remained below measurement granularity ($\approx 100$ ms).
\end{itemize}
This confirms that corrupted model updates cannot permanently disable the appliance in the field.

\subsection{Hardware Watchdog (WDT) Recovery}

The hardware watchdog was able to reboot the system after a fake scheduler exhaustion. The initial test involved too aggressive inactivity watchdog which resulted in two false reboots during the initial phase of the test. This is why the $\Delta t$ had to be re-adjusted. The total reboot time, from the moment the system freezes to the point where the system is ready to accept commands was less than 1 minute in the given test environment. Note that this time can vary depending on the hardware and a particular bootloader implementation.

\subsection{Zero-Touch Provisioning Speed}
From the moment a factory-reset device is connected to power and the network, the automated certificate exchange, image pulling, and initialization sequence required an average of 3 minutes and 15 seconds to reach an active monitoring state.

\subsection{Limitations}
The reliability mechanisms expose several structural limitations:
\begin{itemize}
    \item \textbf{Finite RAM-Disk Capacity:} The \texttt{tmpfs} upper layer is bounded by physical memory; unbounded log emission during sustained network partitions triggers OOM failures if not strictly rotated.
    \item \textbf{Firmware Protection Limits:} OverlayFS immutability protects the OS root but does not prevent malicious lower-level bootloader or baseband firmware modifications.
    \item \textbf{TPM Hardware Dependence:} The Zero-Touch Provisioning sequence relies on hardware TPM 2.0, limiting portability to boards lacking this module.
    \item \textbf{Flash Controller Variability:} While root immutability reduces write amplification, proprietary SD card wear-leveling algorithms introduce hardware-specific variance outside OS control. Quantitative flash endurance modeling is addressed separately in Paper 12.
    \item \textbf{Limited Fleet Scale:} Validation was conducted on a controlled testbed; fleet-scale behavior across heterogeneous hardware and network conditions remains unvalidated.
    \item \textbf{Controlled Power-Failure Simulation:} Power cycles were simulated via automated relay switching; real-world brownouts, voltage sag, and transient instability patterns may differ.
    \item \textbf{Absence of Multi-Year Observation:} Long-duration appliance behavior under continuous operation has not been evaluated; filesystem aging, SD-card degradation, and bootloader drift may emerge over extended horizons.
    \item \textbf{Watchdog False Positives:} During threshold tuning, overly aggressive inactivity detection caused unintended reboots, indicating sensitivity to calibration under variable workloads.
\end{itemize}

% XII. CONCLUSION
% ==========================================
\section{Conclusion}

This work analyzed the lifecycle engineering required to deploy resilient edge appliances in infrastructure-constrained environments. The contribution focuses on immutable-state recovery, bounded deployment failure containment, and autonomous appliance restoration.

By combining a read-only OverlayFS root, containerized Blue/Green OTA rollback, hardware watchdog supervision, and TPM-backed provisioning, the architecture demonstrated stable behavior across repeated power interruptions, simulated update corruption, and induced scheduler exhaustion within the evaluated test environment. Mutation confinement through OverlayFS ensures that corruption domains are spatially bounded and reboot semantics restore clean operational state.

Within the ScholarMaster architecture, this framework operates exclusively as the immutable deployment lifecycle and appliance-hardening subsystem---enforcing recovery boundaries and stabilizing unattended deployment without optimizing flash endurance (Paper 12), validating runtime enforcement semantics (Paper 18), managing federated adaptation (Paper 13), or deriving formal verification theorems (Paper 21).
