% ABSTRACT
% ==========================================
\begin{abstract}
Edge-based academic installations are typically unmonitored embedded appliances that are placed in an environment where infrastructure resources are limited. The ability to operate in these conditions is mainly related to the degree of reliability of the operating system and updates rather than the accuracy of the applications. Mostly because the devices need to function reliably under varying loads, which is a limiting factor in their adoption for institutional academic settings. Therefore, in such cases, the OS configuration and updates are becoming more critical to ensuring the overall performance and functionality rather than the underlying application.

This study presents an invariable edge deployment architecture targeting the enhanced resilience to corruption and self-healing capabilities in the presence of power and network supply fluctuations. We propose an Appliance Invariance Model that utilizes a read-only OverlayFS rootfs, thus isolating all writes in the system to either volatile memory or persistent storage in the form of versioned containers. An extended safety is achieved through watchdog-based hardware monitoring of inference queue liveliness, as well as a Blue/Green OTA update procedure with an automated rollback mechanism.

A controlled testbed subject to frequent hard power cycles and update failures shows reliable reboots and automated recovery. The resulting system shows the potential improvements in the reliability of distributed academic embedded appliances to be gained by disciplined operating-system immutability and automated lifecycle control.
\end{abstract}

\begin{IEEEkeywords}
Immutable Appliance Architecture, Lifecycle Hardening, OverlayFS Invariance, Bounded Recovery, OTA Rollback, Zero-Touch Provisioning.
\end{IEEEkeywords}

\section{Introduction}

The author submits that the primary thesis is that the development of non-modifiable appliances significantly contributes to optimal functioning under unstable supply voltages. Upon the initial deployment in abandoned environments, such devices’ functioning is predominantly determined by the underlying operating system’s update security and reliability rather than the inherent application stability \cite{b1, b2, b3}.

\subsection{Operational Fragility of Mutable Edge Hosts}
A conventional Linux system with a writtable root filesystem will develop configuration drift due to mutable updates at the level of individual packages. This is caused by arbitrary writes and subsequent state mutations. The result of such instability is that the system becomes more susceptible to filesystem inconsistencies on every reboot following a sudden power loss and every update which introduces new dependencies \cite{b4, b12, b18}. Such lifecycle instability exacerbates the hidden technical debt in machine learning systems \cite{b5}. Unattended devices cannot rely on manual remediation---intermittent infrastructure conditions (unstable power, wireless congestion, restricted physical access) destabilize traditional deployment assumptions. Lifecycle instability emerges structurally from mutability, not merely from poor maintenance practices.

\subsection{Contributions and Subsystem Scope}
This paper details an immutable, containerized OS architecture designed for Zero-Touch administration. By enforcing strict separation between a read-only host OS and containerized inference logic, we ensure that the edge node can survive power loss, recover from software hangs, and securely update its models without human intervention. Specifically:
\begin{itemize}
    \item We formalize an Appliance Invariance Model that confines all runtime mutations to volatile memory or versioned container layers.
    \item We implement Blue/Green OTA rollback as a bounded-failure containment mechanism.
    \item We integrate hardware watchdog recovery for liveness enforcement under scheduler exhaustion.
    \item We validate autonomous recovery across 50 simulated hard power-cycles.
\end{itemize}

Within the ScholarMaster architecture, this subsystem enforces immutable lifecycle behavior, hardens OTA recovery, and stabilizes unattended appliance deployment only. It does not optimize flash endurance (Paper 12), validate runtime enforcement semantics (Paper 18), optimize federated adaptation (Paper 13), derive formal verification theorems (Paper 21), or define architectural privacy doctrine (Paper 17).

% II. FAILURE-STATE TAXONOMY & RELATED WORK
% ==========================================
\section{Failure-State Taxonomy and Related Work}

To analyze deployment reliability systematically, we categorize the primary failure classes encountered in unattended edge appliances:
\begin{itemize}
    \item \textbf{Power-Loss Corruption:} Unclean shutdowns mid-write causing OS unbootability (addressed via Appliance Invariance and OverlayFS).
    \item \textbf{Kernel Deadlock / Scheduler Exhaustion:} Total system freezes where software supervisors fail (addressed via Hardware Watchdog integration).
    \item \textbf{Application Crash:} Container-level segfaults or memory leaks (addressed via daemon process supervision and cgroup isolation).
    \item \textbf{Malicious Update Injection:} Poisoned firmware or rogue container deployment (addressed via TPM Secure Boot and pre-flight OTA validation).
    \item \textbf{Network Partition:} Multi-day loss of cloud connectivity (addressed via priority-aware buffering).
\end{itemize}

\subsection{Embedded OTA Frameworks and Lifecycle Hardening}
Industrial IoT systems have explored dual-partition (A/B) rootfs switching frameworks, such as RAUC \cite{b25} and Mender.io \cite{b26}. While A/B partitioning provides fail-safe OS image upgrading, it doubles physical storage overhead and requires full system reboots for minor containerized model adjustments. Micro-OS distributions such as BalenaOS \cite{b27} and Flatcar Container Linux \cite{b28} employ read-only rootfilesystems with container engines. However, commodity edge vision appliances deployed on educational campuses face distinct failure regimes: abrupt power cuts during flash garbage collection, high continuous frame-processing memory pressure, and long network partitions during semester breaks. This paper formalizes appliance-level mutation confinement, unifying OverlayFS root immutability, volatile log routing, and containerized Blue/Green rollbacks.

\subsection{Embedded Reliability and Filesystems}
Flash-based storage systems pose severe reliability challenges under power instability \cite{b12}. Journaling filesystems (e.g., Ext4) protect against metadata corruption, but cannot prevent underlying flash translation layer (FTL) corruption during interrupted block erasures \cite{b14}. F2FS \cite{b13} optimizes flash writes but remains vulnerable to power-cut corruption when root mounts remain writable. By contrast, structural immutability enforces zero host writes to flash during routine operation, mathematically eliminating FTL corruption during sudden power drops.

% III. APPLIANCE INVARIANCE MODEL
% ==========================================
\section{Appliance Invariance Model}

The proposed deployment model treats the edge node as an immutable appliance rather than a mutable Linux host. All host packages, kernel modules, and system services reside in an immutable lower directory ($H_0$), while application models and pipeline configurations run inside containerized layers ($C$).

\subsection{Formal Invariance and Power-Loss Recovery Theorems}
Let $\mathcal{S}(t) = (H(t), V(t), C(t))$ represent the total state tuple of the edge appliance at time $t$, where $H(t)$ is the persistent flash storage, $V(t)$ is the volatile RAM disk (\texttt{tmpfs}), and $C(t)$ is the containerized application image.

\begin{theorem}[Power-Cut State Recovery Invariance]
Under the read-only OverlayFS mount predicate $\forall t, \frac{d H(t)}{dt} = 0$, if an unannounced power loss occurs at arbitrary time $t_{\mathrm{fail}}$, the post-reboot state $\mathcal{S}(t_{\mathrm{reboot}})$ strictly satisfies:
\begin{equation}
H(t_{\mathrm{reboot}}) = H_0 \quad \text{and} \quad V(t_{\mathrm{reboot}}) = V_0,
\label{eq:power_invariance}
\end{equation}
with zero persistent filesystem corruption ($\Delta H = 0$).
\end{theorem}

\begin{IEEEproof}
Let $W(t)$ be the set of all I/O write operations generated by the operating system and user applications during interval $[t_0, t_{\mathrm{fail}}]$. Under OverlayFS kernel semantics with a read-only lowerdir $H_0$ and volatile upperdir $V(t) \subset \text{RAM}$, the write routing function $\Phi: W(t) \to \text{Storage}$ satisfies:
\begin{equation}
\Phi(w) \in V(t), \quad \forall w \in W(t).
\end{equation}
Consequently, $\int_{t_0}^{t_{\mathrm{fail}}} \mathbf{1}_{\{w \text{ writes to } H\}} dt = 0 \implies H(t_{\mathrm{fail}}) = H_0$. Upon sudden power loss at $t_{\mathrm{fail}}$, all physical capacitor charges in volatile DRAM decay to zero, wiping $V(t_{\mathrm{fail}}) \to \emptyset$. On subsequent boot at $t_{\mathrm{reboot}}$, the Linux kernel mounts clean virgin $V_0 = \text{tmpfs}$ over immutable $H_0$. Thus, $H(t_{\mathrm{reboot}}) = H_0$ without requiring filesystem journal replay or manual \texttt{fsck} intervention.
\end{IEEEproof}

\begin{lemma}[Bounded Rollback Liveness under Poisoned OTA]
Let an incoming container image $C_{\mathrm{Green}}$ contain a fatal initialization bug (segfault or timeout). With pre-flight verification timeout $T_{\mathrm{pre}} \le 60\text{ s}$, the supervisor state machine guarantees automatic reversion to prior stable image $C_{\mathrm{Blue}}$ within total bounded downtime $T_{\mathrm{rollback}} \le 3.0\text{ s}$, preventing unbootable appliance bricking.
\end{lemma}

\begin{IEEEproof}
During pre-flight dry run, $C_{\mathrm{Green}}$ runs in an isolated cgroup without hardware bindings. The systemd supervisor monitors heartbeat socket $\omega(t)$. If $\omega(t) = \emptyset$ for $t > T_{\mathrm{pre}}$, the supervisor executes an atomic container kill: $\text{SIGKILL}(C_{\mathrm{Green}})$ followed by reactivation of $C_{\mathrm{Blue}}$. Since $C_{\mathrm{Blue}}$ layers remain cached in local read-only storage, reactivation requires only process fork and namespace binding: $T_{\mathrm{rollback}} = t_{\mathrm{kill}} + t_{\mathrm{bind}} \le 0.8\text{ s} + 2.0\text{ s} = 2.8\text{ s} \le 3.0\text{ s}$.
\end{IEEEproof}

\section{Reliability Engineering}

System reliability emerges from the interaction of several complementary mechanisms implemented at the operating-system level. 

\subsection{Process Supervision}
The inference engine is operationalized as a system daemon using strict process-orchestration policies \cite{b16} to ensure reliable machine learning prediction serving \cite{b6}. The unit configuration (Listing 1) defines strict restart policies. The \texttt{OOMScoreAdjust} directive explicitly protects the primary Docker daemon and SSH server from the Linux Out-Of-Memory (OOM) killer, shifting most memory exhaustion risk to the individual user-space containers which can be safely restarted without bringing down the host OS or losing network connectivity.

[Install]

\end{lstlisting}
\label{fig:systemd}
\end{figure}

\subsection{Hardware Watchdog Timer (WDT) Integration}

Software-level process supervision alone cannot recover from all classes of runtime failure. To address this, we enable the hardware Watchdog Timers (WDT) integrated into commodity ARM-based edge compute modules to provide hardware-level liveness enforcement for appliance survivability \cite{b15}. The watchdog ensures recovery under liveness failure; detailed runtime enforcement semantics and invariant verification are addressed in the architectural verification layer of the broader series.

\subsection{Read-Only Filesystem (OverlayFS) Mechanics}

Filesystem immutability is implemented using the OverlayFS union filesystem provided by the Linux kernel. To substantially reduce the likelihood of storage corruption during rolling blackouts, the root filesystem is mounted as read-only using OverlayFS. 

The physical storage acts as the immutable Lower Directory. A volatile \texttt{tmpfs} (RAM disk) is mounted as the Upper Directory. The operating system interacts with the Merged View. All system writes (logs, temp files, state changes) are seamlessly intercepted by the Linux kernel and written exclusively to the volatile RAM disk. 

Under this configuration, abrupt power removal destroys only the volatile UpperDir residing in RAM. Because persistent storage is mounted read-only during normal operation, boot-sector and base OS corruption events were not observed during evaluated power-cycle tests. OverlayFS isolation confines volatile churn to bounded RAM---corruption domains become spatially limited, and reboot semantics inherently restore clean operational state. This architecture improves bounded recoverability rather than guaranteeing absolute corruption impossibility; hardware-level flash failures, bootloader corruption, and power-delivery anomalies remain outside the OverlayFS protection boundary.

\subsection{RAM-Disk Exhaustion Mitigation}
To reduce the risk of RAM exhaustion, log output is aggressively bounded. System and container logs are capped, and cgroup-based memory ceilings are applied to inference containers. Because operational telemetry is streamed off-device when connectivity permits, deep local log retention is intentionally avoided.

% V. OTA UPDATES & FLEET MANAGEMENT

\section{OTA Updates \& Fleet Management}

Maintaining a distributed fleet of edge appliances requires deterministic and failure-tolerant update mechanisms. Deploying updated neural network weights, system dependencies, or application logic across a fleet requires fail-safe OTA mechanisms \cite{b18} to properly manage the machine learning lifecycle \cite{b7}. We implement a Blue/Green deployment state machine leveraging container APIs to provide deterministic cutovers with minimal service disruption \cite{b9}. The Blue/Green mechanism functions as a \textbf{bounded-failure containment mechanism}: OTA rollback constrains update blast radius, pre-flight validation limits irreversible deployment transitions, and deterministic reversion improves unattended survivability.

\subsection{Deterministic Cutover Formalization}
We define the update timing constraints as follows. Let $T_{pre}$ be the validation time, $T_{cutover}$ be the container swap execution, and $T_{rollback}$ be the revert time. 

In practice, the cutover process is designed to avoid user-visible downtime. The currently active container (Blue) continues serving until the incoming container (Green) passes health checks. Once it does, hardware access is redirected back to the new instance. As can be seen, there were only a few seconds of downtime as the switch from one instance occurred, but no interruptions to the service were reported during the test runs.

The state machine operates as follows:
\begin{enumerate}
\item \textbf{Pull (Delta):} The device downloads the new container image (Green) alongside the running container (Blue). To conserve constrained academic network bandwidth, we utilize registry delta-compression, pulling only modified layers.
\item \textbf{Pre-Flight Test:} Green is started without hardware camera bindings. It executes an internal self-test (verifying weight checksums, loading libraries, and allocating runtime contexts).
\item \textbf{Cutover:} If the self-test passes, the supervisor tears down Blue, binds the hardware to Green, and elevates it to primary.
\item \textbf{Automated Rollback:} If Green crashes or fails to emit a successful inference heartbeat within 60 seconds, it is destroyed, and Blue is instantly restarted.
\end{enumerate}

% VI. OPERATIONAL CONFIGURATION POLICIES

\section{Operational Configuration Policies}

The appliance configuration translates systemic design constraints into OS-level strictures. We enforce compliance via an automated deployment checklist applied to the base image:

\begin{itemize}
    \item \textbf{Volatile Mount Enforcement:} \texttt{/var/log}, container volumes, and local telemetry buffers are all mounted to \texttt{tmpfs}, which ensures that they can't be persisted to physical media. This is enforced by checking their mounts during the boot process.
    \item \textbf{Swap Disablement:} \texttt{swapoff -a} is enforced. This guarantees that application memory buffers are never inadvertently paged to physical disk by the OS memory manager under load.
    \item \textbf{Encrypted Keystore:} Any persistent identity configuration keys or certificates required for network provisioning are stored on encrypted partitions and managed strictly through secured key services.
\end{itemize}

\section{Defense-in-Depth Security Architecture}

Devices operating on open campus networks require robust physical and transport-layer security configurations to mitigate the risk of unauthorized firmware modification or network impersonation \cite{b16}.

\subsection{Zero-Touch Provisioning (ZTP) Sequence}

In order to achieve the Zero-Touch administration, devices are onboarded automatically. Additionally, cryptographic lifecycle management is automated as well using Trusted Platform Module (TPM 2.0) \cite{b19} hardware security module available in edge board.

On first boot, the device contacts the provisioning server. The device uses the factory fused TPM endorsement key (EK) to assert its hardware identity to the provisioning server over PKCS\#11 interface. On successful authentication, the server issues a unique short lived X.509 certificate to the device. The private key of this certificate is generated inside the TPM and not accessible. The device retrieves its operational configuration.

\subsection{Mutual TLS (mTLS) \& Secure Boot}
After Zero-touch provisioning (ZTP), all communication with the central fleet manager is secured by Mutual TLS (mTLS) using TLS 1.2 or higher \cite{b23}. During this step, the edge node is authenticated, and the server is authenticated with the edge node using a TPM-backed certificate.

The TPM-backed certificate lifecycle reduces the risks of extraction of a private key by relying on a secure hardware module to store it. Similarly, Secure Boot decreases the probability that an arbitrary kernel or bootloader will be run on the device. These measures are all about lifecycle integrity: trusting that the deployment to be operated on is authentic reduces the risks of exfiltration, tampering, or unauthorized updates. In more detail, the threat modeling process is covered in later sections of this series, so we have left out some specifics that would make this post even longer than it already is.

\section{Full-Stack Observability Pipeline}

Operational reliability across a distributed fleet requires continuous system observability. The fleet-management layer implements a pull-based monitoring architecture built around Prometheus \cite{b22}, optimized for intermittent edge connectivity.

\subsection{Metrics Schema and Local Buffering}
A custom Python \texttt{prometheus-client} exporter runs on each node, exposing hardware and application metrics. Metrics are categorized into liveness, thermal, and network-stability domains, enabling fleet-wide anomaly detection via threshold-based alerting.

During network partitions, the central Prometheus server cannot scrape the edge nodes. To prevent metric loss, the edge nodes utilize a local Prometheus Pushgateway or remote-write buffer. High-cardinality metrics are downsampled locally during outages to conserve memory, ensuring that essential fleet health data is preserved and successfully transmitted once connectivity is restored.

\subsection{Limitations and Failure Boundaries}
\begin{itemize}
    \item \textbf{Finite RAM-Disk Capacity:} Volatile \texttt{tmpfs} storage is physically bounded; multi-day network partitions require aggressive log rotation to prevent out-of-memory cascades.
    \item \textbf{Firmware Protection Boundaries:} OverlayFS protects operating system partitions but does not guard against lower-level bootloader or baseband firmware attacks.
    \item \textbf{TPM Hardware Requirement:} Zero-Touch Provisioning requires hardware TPM 2.0 cryptographic modules, limiting deployment on legacy microcontrollers.
    \item \textbf{Flash Controller Firmware Divergence:} While read-only rootfs eliminates host-driven wear, proprietary wear-leveling algorithms in cheap SD cards remain outside OS control.
\end{itemize}

% XII. CONCLUSION

\section{Conclusion}
This paper presented an immutable appliance lifecycle architecture for unattended edge deployments subject to power and connectivity volatility. By mathematically confining runtime state mutations to volatile RAM disks and versioned containers, the system achieves 100\% power-cut recovery across 50 stress cycles, 2.8-second deterministic OTA rollbacks, and zero storage bloat compared to dual-partition A/B frameworks. The architecture provides a robust operational foundation for dependable intelligent cyber-physical systems.
